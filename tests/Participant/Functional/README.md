# Participant and reconciliation contracts

These suites characterize Participant identity, mutations and reconciliation before replacing the account implementation. Follow the [PHPUnit ADR](../../../ADR/001-phpunit_tests.md) and its [technical guides](../../../docs/tests/README.md).

Unit tests in `tests/Entity`, `tests/Service/ParticipantHelperTest.php` and `tests/Service/ContributionsReconcilierTest.php` exercise public domain methods with real Participants, Users, contributions, steps and requirements. `ContributionsReconcilierTest` reaches the shared reconciliation rules through `ProposalReconcillier::reconcile()` and `ReplyReconcilier::reconcile()`, including identity conflicts and closed steps for both target identities. No subclass exposes protected methods. `tests/Service/VotesReconcilierTest.php` retains its existing discovery path but now exercises the complete vote matrix through HTTP and real Doctrine persistence: both step types, both target identities, minimum/maximum limits, budget boundaries, ranking, duplicates and empty ballots. Every case reloads the established ballot, verifies ownership and positions, replays the identity action and checks an unrelated participant ballot. Setup is flushed and the EntityManager is cleared before the request, so preparation cannot leave stale inverse collections in the workflow. Indexation remains stubbed; these assertions prove SQL effects only. The maximum-limit cases also characterize login retaining an empty source identity after its votes are deleted; the ballot stays unchanged when login is replayed.

HTTP suites share `ParticipantWebTestCase`, which extends the transactional `AccountWebTestCase`. Fixtures provide explicitly selected collect, selection and questionnaire contexts; scenario identities and contributions are created separately. The shared harness clears the EntityManager before every HTTP request so the action loads persisted relations. SQL writes use the test kernel's connection and roll back after each scenario. Changed flags and sessions are restored by the parent harness. Elasticsearch and outgoing messages are replaced at their boundaries: these tests cover SQL effects, not search, external indexation or delivery.

`ContributionReconciliationTest` triggers reconciliation through login with participation cookies for User targets, and phone verification for Participant targets. It reloads proposal/reply ownership and associated answers after the requests. Conflict and closed-step retention are checked through login; both target types are also covered by the public unit matrix. The closed-step phone-merge loss is separately characterized in `ParticipantMutationTest`.

`VoteReconciliationTest` verifies persisted distinct ballots through the phone mutation and the interactive-login workflow, including source removal, duplicate removal and token replay. Its failure scenario injects an indexer error before any consumer is initialized, sends the HTTP mutation and checks both the error response and the partial SQL effects before test cleanup: the duplicate has already been deleted, the remaining votes retain their previous owners and the source phone has been confirmed. This `CharacterizationGap` documents the lack of workflow atomicity; it does not test a manually supplied rollback or establish a permanent product requirement.

`ParticipantMutationTest` checks phone verification, consent/token preservation, session authentication and deletion authorization through `/graphql/internal`, including persisted refusal effects. `tests/Mutation/SendParticipantPhoneValidationCodeMutationTest.php` now uses the same HTTP harness to verify normalization, retry count, provider errors and the actual stored SMS requests. SMS provider success/error scenarios construct the real mutation with a kernel stub reporting `prod`, then immediately restore the HTTP test kernel. This exercises the provider branch without credentials or network access. Other scenarios retain the deliberate test-mode bypass and do not validate a real SMS code.

The [Jest API guide](../../../docs/tests/jest/api-graphql.md) recommends the API runner for new GraphQL contracts. These existing HTTP PHPUnit scenarios retain the SQL transaction and controlled SMS/indexer boundaries needed for their distinct integration risks; they are not duplicated in Jest. The scoped reconciliation commit contains no Jest test files.

Cases labelled `CharacterizationGap` expose current limitations, not permanent product requirements. See [the audit](../../../user-tests-audit.md) for outstanding production decisions.

CircleCI discovers every concrete class through `tests/**/*Test.php`. The three Cypress workflow specs retain three independent scenarios each, restoring MySQL, Elasticsearch and queues before and after each one-scenario suite. Their scenario data is deterministic, their mutations are awaited, and their success assertions require an HTTP 200 response, no GraphQL errors and a nonempty redirect URL. Test orchestration uses Castor, as required by `AGENTS.md`.

Historical Cypress validation required rebuilding development assets with a temporary TypeScript target override after `graphql: Unexpected invocation` in `admin-next/shared/navbar/NavBarQuery.tsx`. See the audit for the current validation result; neither a local run nor discovery checks establish a successful remote CI run.
